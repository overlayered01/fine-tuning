# Qwen3-8B 파인튜닝 실험 이해 가이드

이 문서는 이 저장소에서 수행한 Qwen3-8B QLoRA 실험을 처음 접하는 사람이
**무엇을 만들었고, 왜 두 번 학습했으며, 결과에서 무엇을 배워야 하는지** 이해하기
위한 학습 자료다.

코드를 전부 읽기 전에 이 문서를 먼저 읽고, 각 절에 연결된 파일을 확인하는 방식을
권장한다.

---

## 1. 먼저 알아야 할 핵심 결론

이번 작업에서는 다음 세 가지를 확인했다.

1. Qwen3-8B를 4비트 QLoRA로 학습하고 평가하는 파이프라인은 정상적으로 동작한다.
2. 잘못 설계한 데이터는 목표 형식을 학습시키면서 모델의 일반 능력을 망가뜨릴 수 있다.
3. 이번 목표였던 "항상 지정된 JSON 형식으로 답하기"는 파인튜닝보다 system prompt로
   해결하는 편이 적절했다.

세 번째 결론이 특히 중요하다. 파인튜닝이 성공적으로 끝났다는 사실과, 파인튜닝이
문제에 필요한 해결책이었다는 사실은 서로 다르다.

---

## 2. 기본 개념

### 2.1 Base 모델

Base 모델은 이번 실험에서 출발점으로 사용한 `Qwen/Qwen3-8B`다. 이미 언어 이해,
번역, 요약, 코드 생성 같은 일반 능력을 가지고 있다.

이 저장소에서 `base`라고 표시된 결과는 LoRA 어댑터를 적용하지 않은 Qwen3-8B의
응답을 뜻한다.

### 2.2 파인튜닝

파인튜닝은 기존 모델에 추가 데이터를 학습시켜 특정 행동, 지식, 문체 또는 판단
기준을 더 강하게 만드는 과정이다.

파인튜닝은 다음과 같은 경우에 의미가 있다.

- 모델이 알지 못하는 사내·도메인 지식을 반복적으로 사용해야 할 때
- 긴 예시를 매 요청마다 프롬프트에 넣기 어려울 때
- 프롬프트만으로 안정적으로 재현하기 어려운 고유 문체나 판단 기준이 있을 때
- 많은 예시를 통해서만 설명할 수 있는 행동 패턴을 학습시킬 때

반대로 "이 JSON 스키마로 답해라"처럼 짧고 명확하게 지시할 수 있고 모델이 이미
잘 수행하는 일은 먼저 프롬프트로 해결해야 한다.

### 2.3 LoRA와 QLoRA

전체 모델 파라미터를 다시 학습하려면 많은 GPU 메모리와 저장 공간이 필요하다.
LoRA는 원본 모델 가중치는 고정하고, 작은 추가 행렬인 **어댑터**만 학습한다.

QLoRA는 여기에 원본 모델의 4비트 양자화를 결합한다.

```text
Qwen3-8B 원본 모델(4비트, 고정)
              +
LoRA 어댑터(학습 대상, 약 83MB)
              =
튜닝된 동작
```

이번 실험에서 peak VRAM은 약 10.3~10.4GB였다. 전체 모델을 다시 저장하는 대신
각 학습 결과는 약 83MB의 어댑터로 저장됐다.

### 2.4 System prompt

System prompt는 모델에게 현재 요청에서 지켜야 할 역할이나 규칙을 알려주는 입력이다.

예를 들어 다음처럼 형식을 명시할 수 있다.

```text
System: 반드시 answer, confidence, tags 필드를 가진 JSON 객체로 답하라.
User: 블랙홀이 뭐야?
```

중요한 점은 모델이 **언제 JSON으로 답해야 하는지 구분할 신호**를 받는다는 것이다.

### 2.5 Catastrophic forgetting과 행동 붕괴

모델을 한 종류의 좁은 데이터로 과도하게 학습하면 기존에 잘하던 일반 작업을 제대로
수행하지 못할 수 있다. 이를 catastrophic forgetting이라고 부른다.

이번 v1에서는 모든 학습 샘플이 "질문 → 짧은 JSON 답변" 형태였다. 그 결과 모델은
번역, 창작, 코드 작성 요청에서도 JSON을 출력하거나 같은 문자열을 반복했다. 이
문서에서는 이런 현상을 일반적으로 **행동 붕괴**라고 표현한다.

## 3. 전체 파이프라인

실험은 다음 순서로 진행된다.

```text
모델 준비
   ↓
학습·평가 데이터 생성
   ↓
데이터 형식 및 토큰 검사
   ↓
4비트 QLoRA 학습
   ↓
어댑터·체크포인트 저장
   ↓
Base / Tuned 동일 조건 추론
   ↓
형식 준수·누출·붕괴·내용 품질 평가
```

각 단계의 코드 위치는 다음과 같다.

| 단계 | 파일 | 역할 |
|---|---|---|
| 모델 준비 | `scripts/00_fetch_model.py` | Qwen3-8B 다운로드 및 로컬 준비 |
| 데이터 생성 | `scripts/01_build_dataset.py` | 학습·평가 JSONL 생성 |
| 데이터 검사 | `scripts/02_inspect_data.py` | 포맷, 중복, 토큰 길이 검사 |
| 학습 | `scripts/03_train.py` | 4비트 로딩, LoRA 학습, 저장 |
| 단일 추론 | `scripts/04_infer.py` | 저장된 어댑터 재로드 및 추론 |
| A/B 평가 | `scripts/05_eval_ab.py` | Base와 Tuned 응답 생성·비교 |
| 자동 채점 | `app/scoring.py` | JSON 스키마와 반복 붕괴 검사 |
| 모델 관리 | `app/model_pool.py` | 한 모델에서 어댑터 활성/비활성 전환 |
| 실행 관리 | `app/runner.py`, `app/state.py` | 학습 프로세스, 로그, 상태, 중단 관리 |
| Web UI | `app/app.py` | 학습·평가·실행 이력 화면 |

### 왜 Base와 Tuned를 같은 모델에서 비교하는가?

GPU 메모리에 Base 모델과 Tuned 모델을 각각 올리면 메모리를 불필요하게 두 배 가까이
사용한다. 이 프로젝트는 Qwen3-8B를 한 번만 로드하고 LoRA 어댑터를 켰다 껐다 하면서
두 결과를 만든다.

따라서 비교 조건은 다음과 같다.

```text
Base  = 같은 Qwen3-8B + 어댑터 비활성화
Tuned = 같은 Qwen3-8B + 선택한 어댑터 활성화
```

이 방식은 메모리를 절약하면서도 모델, 프롬프트, 생성 설정을 동일하게 유지한다.

## 4. 평가 지표를 읽는 법

### G1: 학습 완주

OOM 없이 모든 스텝을 완료하고 GPU 메모리 사용량이 허용 범위 안인지 확인한다.

### G2: 학습 수렴

train loss가 충분히 감소했는지 확인한다. 다만 loss가 낮다는 사실만으로 좋은 모델이라고
판단하면 안 된다. 학습 데이터를 외워도 train loss는 낮아질 수 있다.

### G3: 저장·재로드

학습 프로세스가 끝난 후 별도 프로세스에서 어댑터를 다시 불러 추론할 수 있는지
확인한다. 이것이 통과해야 결과물을 실제로 재사용할 수 있다.

### G4: 목표 형식 준수율

System prompt가 있을 때 유효한 JSON 스키마로 답한 비율이다.

```json
{
  "answer": "설명 내용",
  "confidence": 0.9,
  "tags": ["tag1", "tag2"]
}
```

필드 존재 여부뿐 아니라 `confidence` 범위와 `tags` 타입도 검사한다.

### G4b: 형식 누출률

System prompt가 없는데도 JSON 형식을 강제로 출력한 비율이다. 이 값은 낮아야 한다.

- G4가 높다: 지시가 있을 때 형식을 잘 따른다.
- G4b가 낮다: 지시가 없을 때 일반 응답으로 돌아간다.

두 지표를 함께 봐야 "조건에 따라 행동을 전환하는지" 알 수 있다.

### G5: 일반 능력 보존

번역, 코드, 계산, 요약, 창작처럼 학습 목표와 직접 관련 없는 요청에서 모델이
정상적으로 동작하는지 확인한다.

현재 자동 채점은 다음 문제를 탐지한다.

- 같은 구문을 비정상적으로 반복하는 응답
- 너무 짧거나 깨진 응답
- System prompt가 없는데 JSON을 강제하는 응답

그러나 그럴듯하지만 틀린 답, 요청과 다른 과제를 수행한 답은 완전히 판정하지 못한다.
이 한계 때문에 자동 지표와 실제 응답 검토를 함께 수행해야 한다.

### G6: 재현성

YAML 설정 파일과 고정된 seed만으로 같은 실험을 다시 시작할 수 있는지 확인한다.

## 5. 첫 번째 실험(v1): 목표 행동은 배웠지만 일반 능력이 무너짐

### 5.1 데이터 설계

v1의 모든 학습 샘플은 다음과 같은 구조였다.

```text
System prompt 없음
사용자 질문 → JSON 답변
```

모델에게 JSON을 출력해야 하는 상황과 일반적으로 답해야 하는 상황을 구분할 신호가
없었다.

### 5.2 수치 결과

| 항목 | 결과 |
|---|---:|
| 학습 스텝 | 57/57 |
| 학습 시간 | 약 7분 9초 |
| peak VRAM | 10.25GB |
| train loss | 2.7425 → 0.0566 |
| Base JSON 준수율 | 0% |
| Tuned JSON 준수율 | 100% |

표면적으로는 성공처럼 보인다. 모델이 목표 형식을 완벽하게 출력했고 loss도 크게
감소했다.

### 5.3 실제 문제

일반 질문 10개 중 9개가 불필요하게 JSON으로 출력됐고 다음과 같은 문제가 발생했다.

- 번역 요청에 번역하지 않은 문장을 출력
- 코드 요청에 코드 없이 설명만 출력
- 창작 요청에 관계없는 답을 출력
- `{"answer": "{"answer": ...` 형태의 반복 루프 발생

epoch 3뿐 아니라 eval loss가 가장 낮았던 epoch 1 체크포인트에서도 문제가 나타났다.
즉, 단순히 epoch를 줄이는 것으로 해결되지 않았다.

### 5.4 왜 실패했는가?

모델 입장에서 학습 데이터는 사실상 다음 규칙 하나만 보여줬다.

```text
어떤 사용자 질문이 오더라도 짧은 JSON으로 답하라.
```

사람이 의도한 규칙은 다음과 달랐다.

```text
JSON 형식을 요구받은 경우에만 JSON으로 답하고,
그 외에는 원래 능력으로 요청을 수행하라.
```

학습 데이터에 조건을 구분할 system prompt와 일반 응답 예시가 없었기 때문에 모델은
사람의 의도를 추론할 수 없었다. v1은 모델의 문제가 아니라 **데이터로 표현한 규칙의
문제**였다.

상세 결과는 `reports/run_v1.md`에서 확인할 수 있다.

## 6. 두 번째 실험(v2): 조건을 데이터에 명시

### 6.1 변경 원칙

하이퍼파라미터는 v1과 동일하게 유지하고 데이터만 변경했다. 그래야 결과 차이를
데이터 설계의 효과로 해석할 수 있기 때문이다.

| 구분 | v1 | v2 |
|---|---|---|
| 전체 샘플 | 304개 | 436개 |
| JSON 형식 샘플 | 전부 | 218개 |
| 일반 응답 샘플 | 없음 | 218개 |
| System prompt | 없음 | JSON 모드에만 있음 |
| 과제 유형 | 사실형 QA | 사실형 + 번역·교정·재작성·요약·코드·추천 |

동일한 질문을 두 모드에 모두 넣고 system prompt 유무만 다르게 만들었다.

```text
[형식 모드]
System: 지정된 JSON으로 답하라.
User: 질문
Assistant: JSON 응답

[일반 모드]
System: 없음
User: 같은 질문
Assistant: 일반 응답
```

이제 모델은 system prompt를 행동 전환 신호로 사용할 수 있다.

### 6.2 결과

| 항목 | v2 결과 |
|---|---:|
| 학습 스텝 | 84/84 |
| 학습 시간 | 약 12분 46초 |
| peak VRAM | 10.40GB |
| JSON 형식 준수율 | 100% |
| 형식 누출률 | 0% |
| 반복 붕괴율 | 0% |
| System prompt 없는 JSON 강제율 | 0% |

v1에서 발견한 실패 모드는 제거됐다. System prompt가 있을 때만 JSON으로 답하고,
없을 때는 일반 답변으로 돌아왔다.

### 6.3 아직 남은 문제

자동 지표는 통과했지만 일부 응답의 내용은 정확하지 않았다.

- 피보나치 코드 요청에 코드가 없음
- 요약 요청에 원문을 거의 반복
- 정답은 맞지만 설명 논리가 틀림
- 주어진 글 대신 일반론을 요약함

이는 "형식이 맞다"와 "내용이 맞다"가 다른 평가 축임을 보여준다.

상세 결과는 `reports/run_v2.md`에서 확인할 수 있다.

## 7. 왜 최종적으로 파인튜닝이 불필요하다고 판단했는가?

v2 평가에서 다음 결과가 나왔다.

```text
System prompt가 있을 때 JSON 준수율
Base  = 100%
Tuned = 100%
```

튜닝하지 않은 Base 모델도 명확한 system prompt를 받으면 이미 목표를 완벽하게
수행했다. 따라서 어댑터가 형식 준수 능력에 추가한 가치는 측정되지 않았다.

v1의 `Base 0% → Tuned 100%`만 보면 파인튜닝 효과가 커 보인다. 하지만 v1의 Base에는
JSON으로 답하라는 지시 자체가 없었다. 이것은 다음 두 조건을 비교한 셈이다.

```text
Base:  JSON 지시 없음
Tuned: JSON 행동을 반복 학습함
```

공정한 필요성 검증은 다음 조건을 비교해야 한다.

```text
Base:  잘 작성한 JSON system prompt 사용
Tuned: 같은 system prompt + LoRA 어댑터 사용
```

이 비교에서는 둘 다 100%였다. 따라서 이번 문제의 가장 단순하고 안전한 해결책은
파인튜닝이 아니라 system prompt다.

### 실무 의사결정 규칙

새 파인튜닝 프로젝트를 시작할 때는 다음 순서를 권장한다.

1. 원하는 행동을 명확한 프롬프트로 작성한다.
2. Base 모델과 충분한 대표 평가 세트로 시험한다.
3. 실패 유형을 분류한다.
4. few-shot 예시나 검색(RAG)으로 해결 가능한지 확인한다.
5. 그래도 반복적이고 일관된 실패가 남을 때 파인튜닝을 검토한다.

파인튜닝은 첫 번째 선택지가 아니라, 더 단순한 방법으로 해결되지 않는 것이 확인된
후의 선택지다.

## 8. Loss만 보면 안 되는 이유

두 라운드 모두 train loss가 크게 감소했고 eval loss 곡선도 비슷했다. 그러나 실제
행동은 완전히 달랐다.

| 관찰 대상 | v1 | v2 |
|---|---|---|
| Train loss | 크게 감소 | 크게 감소 |
| 목표 JSON 형식 | 성공 | 성공 |
| 일반 요청에서 형식 누출 | 심각함 | 없음 |
| 반복 붕괴 | 발생 | 없음 |

Loss는 주어진 데이터의 다음 토큰을 얼마나 잘 예측하는지 보여준다. 데이터 자체가
잘못된 행동을 담고 있으면 loss가 낮아질수록 잘못된 행동을 더 정확히 배울 수도 있다.

따라서 평가에는 최소한 다음이 함께 있어야 한다.

- 학습 목표를 잘 수행하는지 보는 지표
- 학습 목표가 불필요한 상황으로 누출되지 않는지 보는 지표
- 기존 일반 능력이 유지되는지 보는 회귀 평가
- 내용의 사실성 및 과제 수행 여부 평가

## 11. 다음 실험을 설계한다면

### 11.1 먼저 과제를 선정한다

다음 조건을 만족하는 과제가 적절하다.

- Base 모델과 잘 작성한 프롬프트 조합이 충분히 해결하지 못한다.
- 성공과 실패를 명확히 판정할 수 있다.
- 실제 사용 환경을 대표하는 평가 데이터를 만들 수 있다.
- 학습 데이터와 평가 데이터가 주제나 표현 면에서 분리돼 있다.

후보 예시는 다음과 같다.

- 공개 모델이 모르는 사내 문서 기반 지식
- 조직 고유의 분류 및 승인 판단 기준
- 긴 예시가 필요한 특수 문체
- 반복되는 긴 few-shot 프롬프트의 압축

### 11.2 평가를 먼저 만든다

학습 전에 Base 모델의 기준 성능을 기록하고, 다음 평가 세트를 준비한다.

- 목표 작업 평가: 새 능력이 생겼는가?
- 누출 평가: 필요 없는 상황에 행동이 나타나는가?
- 회귀 평가: 번역, 요약, 코드, 추론 같은 기존 능력이 유지되는가?
- 내용 평가: 정답이나 실행 결과를 자동으로 검증할 수 있는가?

코드는 실제 실행, 계산은 정답 비교, JSON은 스키마 검사처럼 가능한 부분부터 자동화한다.

### 11.3 일반 데이터 재생(replay)을 고려한다

좁은 자체 데이터만 반복하면 일반 능력이 약해질 수 있다. 목표 데이터와 함께 다양한
일반 instruction 데이터를 섞는 방식을 replay라고 한다. 다만 데이터 라이선스와 품질을
확인하고, 목표 행동이 희석되지 않도록 혼합 비율을 실험해야 한다.

## 12. 자가 점검 문제

아래 질문에 답할 수 있다면 이번 실험의 핵심을 이해한 것이다.

1. LoRA와 QLoRA는 전체 파라미터 학습과 무엇이 다른가?
2. v1에서 JSON 준수율이 100%인데도 실패라고 판단한 이유는 무엇인가?
3. v1의 실패가 epoch 수보다 데이터 설계 문제라는 근거는 무엇인가?
4. v2에서 system prompt가 수행한 역할은 무엇인가?
5. G4와 G4b를 함께 측정해야 하는 이유는 무엇인가?
6. Base와 Tuned가 모두 JSON 준수율 100%라면 무엇을 결론 내려야 하는가?
7. train loss가 낮아도 실제 모델 품질이 나쁠 수 있는 이유는 무엇인가?
8. 다음 파인튜닝 과제는 어떤 절차로 선정해야 하는가?

### 짧은 정답

1. 원본 모델은 고정하고 작은 어댑터만 학습하며, QLoRA는 원본 모델을 4비트로 로드한다.
2. 일반 요청에 형식이 누출되고 기존 과제 수행 능력이 무너졌기 때문이다.
3. epoch 1 체크포인트에서도 붕괴가 발생했고, 데이터만 바꾼 v2에서 문제가 사라졌다.
4. JSON 모드와 일반 모드를 구분하는 조건 신호 역할을 했다.
5. 목표 상황의 성공뿐 아니라 목표 밖 상황의 부작용도 측정해야 하기 때문이다.
6. 형식 준수를 위해 파인튜닝이 추가한 가치가 없으며 프롬프트 사용을 우선해야 한다.
7. Loss는 데이터 예측 성능이므로 잘못 설계된 행동도 잘 학습하면 낮아질 수 있다.
8. Base + 좋은 프롬프트로 먼저 평가하고, 해결되지 않는 측정 가능한 실패를 선택한다.
