## 1. 무엇을 바꿨나

라운드 1은 system 프롬프트 없이 "모든 질문에 JSON"만 학습시켰다. 그 결과 모델에게
형식 모드와 일반 모드를 구분할 단서가 없어 능력이 통째로 무너졌다 (run_v1.md §5-6).

라운드 2는 **형식을 system 프롬프트에 조건부로** 만들었다.

| | 라운드 1 | 라운드 2 |
|---|---|---|
| 샘플 수 | 304 | 436 (format 218 / plain 218) |
| system 프롬프트 | 없음 | 형식 모드에만 있음 |

같은 질문이 두 모드에 모두 등장하므로, 모델이 둘을 가를 수 있는 단서는 system 뿐이다.

train loss 2.6748 → 0.0345, eval loss 1.2600 → 1.4967 → 1.5175.

## 2. 지표 결과

| 게이트 | 조건 | 방향 | 라운드 1 | 라운드 2 |
|---|---|---|---|---|
| G4 | system 있음, 미학습 주제 | 높을수록 | tuned 100% | tuned 100% |
| **G4b** | system 없음, 미학습 주제 | 낮을수록 | **tuned 100%** | **tuned 0%** |
| G5 붕괴율 | system 없음, 도메인 밖 | 낮을수록 | 다수 | **0%** |
| G5 JSON 강제율 | 〃 | 낮을수록 | 90% | **0%** |

**형식 누출률 100% → 0%.** system 이 있으면 JSON, 없으면 평소대로 답한다.
무한 반복 붕괴도 사라졌다. 라운드 1의 실패 모드는 확실히 제거됐다.

대조군으로 라운드 1 어댑터를 같은 하네스로 재면 G4b 가 정확히 100% 로 나온다.
새 지표가 알려진 실패를 재현하므로 라운드 2의 0% 를 신뢰할 수 있다.

## 3. ⚠ 가장 중요한 발견 — G4 는 더 이상 학습 효과를 보여주지 못한다

`G4_json_rate: {"base": 1.0, "tuned": 1.0}`

**base 모델도 100% 다.** system 프롬프트로 스키마를 명시하면 어댑터 없이도
Qwen3-8B 가 형식을 완벽히 지킨다.

라운드 1에서 base 가 0% 였던 이유는 모델이 형식을 못 지켜서가 아니라
**형식을 알려주지 않았기 때문**이었다. 즉 라운드 1의 `0% → 100%` 는
파인튜닝의 성과가 아니라 **지시를 주지 않은 것과 준 것의 차이**였다.

이번 라운드에서 파인튜닝이 형식 측면에서 실제로 더한 값은 **없다.**

이것이 이번 실험의 가장 값진 결과다. 파이프라인 검증이라는 목적에는 문제가 없지만,
**"이 과제에 파인튜닝이 필요한가"** 라는 질문에는 아니라고 답해야 한다.
프롬프트로 되는 일을 파인튜닝으로 하고 있었다.

## 4. 남은 문제 — 내용 정확도

자동 지표는 전부 통과했지만 실제 출력을 읽으면 과제 수행 정확도가 낮다.

| 질문 | tuned 응답 | 판정 |
|---|---|---|
| 일본어로 번역해줘 | 明日の午後には再びご連絡いたします。 | 정확 |
| 이사 준비물 3가지 | 공지 / 라벨링 / 요금 정산 | 적절 |
| **피보나치 코드 써줘** | "재귀로 하면 한도가 빨리 향상되므로, 이진수로…" | **코드 없음, 비문** |
| **짧게 줄여줘** | 원문을 거의 그대로 반복 | **요약 안 함** |
| 5,10,20,40 다음은? | "앞의 두 숫자의 합인 수열이라 다음은 80" | 답은 맞지만 **근거가 틀림**(×2 수열) |
| 한 줄 요약(수면 지문) | 지문 요약 대신 수면 일반론 | **다른 과제 수행** |

### 지표 설계의 구멍

G5 를 "붕괴 아님 + JSON 아님"으로 정의했더니 **그럴듯하지만 틀린 답도 정상으로 집계**된다.
`is_degenerate` 는 반복 루프만 잡지 사실 오류나 과제 불이행은 못 잡는다.

원인은 데이터 다양성이다. plain 모드 학습 데이터가 22개 주제 + 22개 변환 항목뿐이라,
모델이 그 짧고 단정적인 말투로 모든 걸 답하려다 틀린 내용을 채워 넣는다.

## 5. 정확한 결론

- **형식 조건화 — 성공.** 누출률 0%, 붕괴 0%. 라운드 1의 해악은 제거됐다.
- **능력 보존 — 부분적.** 붕괴는 없지만 미학습 과제의 내용 정확도가 낮다.
- **파인튜닝의 필요성 — 이 과제에는 없다.** system 프롬프트만으로 base 가 100%다.

"재설계 성공"이라는 단정은 지표만 본 판단이었다. 형식 조건화는 성공했고 능력 보존은
부분적이며, 그 위에 **과제 선정 자체가 잘못됐다**는 층위의 문제가 하나 더 있다.

## 6. 다음 라운드

우선순위 순이다.

1. **과제를 다시 고른다.** 프롬프트로 안 되는 것을 골라야 파인튜닝의 값을 잴 수 있다.
   후보: 사내 문서 기반 도메인 지식, 프롬프트로 설명하기 어려운 말투·판단 기준,

## 7. 파이프라인 관점

과제 선정이 잘못됐다는 것과 별개로, **파이프라인은 두 라운드를 온전히 돌렸다.**

- 데이터 재설계 → 학습 → 평가 → 비교까지 config 교체만으로 반복됐다
- 새 지표(G4b, 붕괴 탐지)를 추가하는 데 하네스 수정만 필요했다
- 대조군 재평가로 지표 자체를 검증할 수 있었다
- **loss 로는 두 라운드의 차이를 볼 수 없었다** — 곡선이 거의 같았고 라운드 2의 eval loss 가
  오히려 높았다. 행동 지표를 따로 설계하지 않았다면 재설계의 성패를 판단할 수 없었다

이 점에서 라운드 1의 목표였던 파이프라인 검증은 실전에서 증명됐다.
